# wiggle 立ち上げの航海日誌

2026-05-22 から 2026-05-27 にかけて、xkep-cae を厳密 FEM から **撚線工程の 3D CG** に
舵を切った。ここまでの記録。

## ピボットの瞬間

> 個人の趣味開発にしては xkep-cae は型にハマりすぎていました。もっと自由にやります。

MCDD・status-N の連番運用・3 指標 AND gate・verification_matrix・契約検査 24 項目。
よく出来た管理だが、撚線が回ってる絵を作って楽しむのに必要なのは別の力だった。

「CAE は本質的に高級アニメーター」という一行で空気が変わって、`wiggle/` が生まれた。

## バックエンド遍歴（短い旅）

1. **matplotlib** で行きそうになる → でも「学術論文風」が CG クリエイター気分と合わない
2. **PyVista** に着地 → VTK の tube レンダリングで一発でそれなりの絵が出る
3. 早くも **three.js** へ → MeshPhysicalMaterial + bloom + ACES toneMapping

PyVista 版は `wiggle/render.py` で残してある。sanity check 用。three.js 版は
`wiggle/web/` に。

## 撚りほどき事件

最初に出した still を見て、

> 撚り工程ではなく撚りほどき工程になっている = 回転と進行方向が両方逆です。

θ(z, t) = +ω·t + 2π(z−z_lay)/L_pitch と素朴に書いていた。これだと
∂z/∂t|_feature = −ωL_pitch/(2π) < 0、つまり helix の模様が upstream に流れる。
撚れていく方向と逆 → 「撚りほどき」表現になっていた。

物理的に正しいのは「z の材料は時刻 t − (z−z_lay)/v_feed にレイプレートを通過した時の
ボビン位相を持っている」で、v_feed = ωL_pitch/(2π) を代入すると
θ(z, t) = φ_i **−** ω·t + 2π(z−z_lay)/L_pitch になる。

`wiggle/kinematics.py` の docstring で物理導出をフルで残している。次に同じ罠を踏まない
ように。

## three.js studio版の手痛い学び

「スタジオ高級感トーン」で進めた:

- HDRI 環境（とりあえず `RoomEnvironment`）
- `MeshPhysicalMaterial` で metalness 0.78、clearcoat 0.85
- bloom strength 0.45、threshold 0.92
- 3-spot lighting + PCF shadow
- 6 色パレット（オレンジ・黄・ティール・青・紫…）で素線をカラフルに

結果:

> チープさが和をかけてチープになってしまいました。

要素を盛れば豪華になるわけではない、の典型例。

**問題の構造**:

1. **本物でないスケール** — 数字が無次元で「1.1」「9.0」と並んでいる。実機の物理寸法を
   無視しているので、近接効果（ボビンが近すぎ）も、視覚比例（pitch と diameter の比）も
   全てが本物っぽくない
2. **カラフル素線** — 撚線の本物は同じ銅・同じ被膜（あるいは無被膜）で、色は分類のための
   ストライプ程度。虹色は「教育玩具」感を呼ぶ
3. **bloom 過剰** — 素線が自己発光してるように見えて「ネオン」になる。金属反射の
   モデルが消える

「派手にする」と「リッチにする」は別物だった。

# 第二航海（2026-05-28）— 工場っぽさを盛る

## 「内なるゴリラが出てくるところでした」

前セッションの「物理寸法 → 銅色 → 距離 → グルグル」を一気に実装したら、
それっぽくなって自分でも気持ちよくなった。ユーザの第一声:

> ウホッ、それっぽい絵ですね。それっぽくて内なるゴリラが出てくるところでした。

調子に乗って盛りに行く方針が決定。要求は 4 つ:

1. ボビンに**素線が巻かれてる**様子（送られてくる感）
2. **撚りダイス**を描画
3. 撚られた線が**ボビンに巻き取られる**
4. **回転速度を上げて工場らしく**

## 巻取りボビンが見えない事件（4 イテレーション）

ここが今回の最大の躓き。巻取りスプールを作って配置したのに、レンダリングしても
**一向に見えない**。原因の特定までに 4 回の試行を要した:

### イテレーション 1: サイズ不足を疑う
TAKEUP_FLANGE_R = 50 では小さすぎた。80 まで増やしたが、まだ見えない。

### イテレーション 2: カメラフレーミング
zCenter が機械の左寄りに置かれていて、右端の巻取りがフレーム外。
zCenter を機械全長の中央に再計算した。それでも見えない。

### イテレーション 3: マテリアルが暗すぎ
巻取りの body マテリアルが `0x3c4148`（ほぼ黒）、フランジが
`bobbinFlangeMat`（こちらも暗い茶）。暗背景に溶け込んでいた。
さらに t=0 では巻線スケールが 0.25 で**ほぼ無**に近い状態。
マテリアルを明るくし、初期スケールを 0.4、サイクルを 60 秒に短縮、simT=3 開始。
それでも見えない。

### イテレーション 4: 背景壁が物理的に遮蔽していた
最後に気づいた原因が一番マヌケで、**背景壁メッシュ（wall）が z≈615 にあり、
巻取り（z=680）を物理的に隠していた**。

```js
// 修正前
wall.position.set(0, machineLen * 0.2, zMid + machineLen * 0.4);  // z≈615
// 修正後
wall.position.set(0, machineLen * 0.2, cfg.z1 + 200);              // z=850
```

**教訓**: シーンに「映らないオブジェクト」がある時、最初に疑うべきは
**カメラフレーミング** ではなく **オクルーダー**。Three.js の Inspector を
入れるか、wireframe モードでデバッグすべきだった。マテリアルやサイズを
いじっても見えないなら、何かが手前にある。

## 「ここからは超簡易物理エンジンが必要かと」

巻取りが見えるようになったら、次の要求:

> 今巻取りボビンの中央に撚られた撚り線が吸い込まれてますね。回転して巻き取れますか？
> ここからは超簡易物理エンジンが必要かと。

「超簡易物理エンジン」というフレーズが好き。本格的な剛体動力学は要らない、
**回転の見た目** が欲しいだけ。

実装した「物理」:

```
v_feed = |ω| × L_pitch / (2π)              # ケーブル線速度 [mm/s]
ω_takeup(t) = v_feed / R_wound(t)          # 巻き径で送り速度を割る
θ_takeup(t) = ∫₀ᵗ v_feed / R(τ) dτ         # 角度は時間積分
```

R(t) が線形に増えていくので、積分は対数関数で解析的に解ける:

```js
theta = v_feed * 60 / dR * Math.log(R_t / R0);
```

時間スライダーで巻き戻しても正確に追従する。incremental に dt 加算するより
こっちが好み。

数字を入れると t=0 で巻取りは 0.87 rad/s、t=60s で 0.346 rad/s に減速。
線速度は一定だが、巻き径が太るほど回転は遅くなる。物理として正しい挙動。

## ダイスと素線の接触（≠FEM のやばい接触）

ユーザの一言:

> ダイスと素線の接触（≠FEM のやばい接触）も考えたい

ジワっと笑ってしまった。xkep-cae でずっと格闘してきた NCP 接触問題ではなく、
**ただの視覚的接触** が欲しい、という宣言。実家のような安心感。

実装は単純に **ダイス内径を素線束外径に合わせる** だけ:

```
DIE_BORE_R = R_layer + outer_radius + 0.5  # 7.8mm
                                            # 素線束外径 7.3mm + 0.5mm クリアランス
```

旧 13.75mm から半減。素線がダイスの内壁に視覚的に触れて通過していく。
ファンネル形状も改修して、入口 12.5mm → ボア 7.8mm のガイドを描画。

**FEM では一生かかっても解けない接触問題が、CG では 1 行で済む**。
本セッションの精神的勝利。

## L_tail_in を伸ばすだけで世界が変わる

「サプライボビンがダイスに近い気がする」の指摘で、L_tail_in を 250→450mm に。
コード上は 1 行の変更だが、視覚的インパクトは大きい:

- ボビンからダイスへの素線収束が緩やかに（タンジェント角が浅くなる）
- 6 本の素線が「広がりからまとまる」流れがちゃんと見える
- ダイスが孤立した小物ではなく「集約点」として機能する

実機の写真と比べると、依然として L_tail_in は短い（実機は数 m）が、
卓上モデルとしては自然な比例になった。

## 教訓集（第二航海）

- **「見えない」≠「描いてない」**: 暗マテリアル / カメラ外 / オクルーダー、
  この 3 つを順に潰す。逆順だと時間を溶かす（今回 4 イテレーション）
- **「超簡易物理エンジン」は最高のフレーズ**: 完全な物理は要らない、
  **挙動の見た目**が欲しいだけ。解析積分で 1 行で済む
- **FEM の難問を CG で解く**: ダイス接触は本来トポロジー込みの厄介な問題だが、
  「視覚的に触れて見える」だけなら BORE_R を調整するだけで済む
- **L_tail_in は安いパラメータ**: 1 行の数字を変えるだけで構図全体が引き締まる。
  視覚デザインで「距離」は最も効くパラメータ

## 次セッションへの申し送り（第二航海）

巻取りスプールに**トラバース機構**（左右往復巻き）を入れると一気にプロっぽくなる。
あと**クレードルの支持アーム**（リングからボビンへの放射状の腕）を追加すると、
ボビン群が宙に浮いて見える違和感が消える。
